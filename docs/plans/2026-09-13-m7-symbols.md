# Milestone 7 — Symbols Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn addresses into names and into source lines — `nlist_64` from every loaded module, DWARF from a `.dSYM` when one can be found — and show both on screen against a live target.

**Architecture:** The engine grows one subsystem and the contract grows four entries. `macho/Image` learns `LC_SYMTAB` (it already refuses to parse what nothing reads); `symbols/Nlist` turns those entries into names through the same `Reader` the module parser uses, so a shared-cache dylib is read from memory and a file on disk from the file; `symbols/Dsym` finds a dSYM; `symbols/Dwarf` reads it through libdwarf; and `symbols/Symbols` is the resolver that joins the two sources per module and answers the contract's questions. Above the C contract nothing learns what a `nlist_64` is, which is the same rule §5 imposes on registers.

**Tech Stack:** C++17, libdwarf 2 from Homebrew (`brew install libdwarf`, formula `dwarfutils`), `LC_SYMTAB`/`nlist_64`, `dsymutil` for the test fixtures, `mdfind` for dSYM discovery, Qt 6 with the vendored `StdTable`, Catch2 v3.14.0, cmkr.

**Spec:** `docs/specs/2026-09-07-macos-port-design.md` — section 8 (symbols: the two sources and dSYM location), section 5 (the contract's rules for buffers and errors), section 12's milestone 7 row, and open research question 2, which this milestone answers.

**Predecessors:** milestones 0 through 6, complete and merged. The engine launches, attaches, stops, reads and writes registers and memory, carries breakpoints, watchpoints and stepping, enumerates modules with their slides and UUIDs, the memory map and threads, and disassembles both architectures. `regview.app` shows all of it, with two self-tests running offscreen in CI.

## Decisions taken before this plan was written

Settled with the project owner on 2026-09-13. Do not reopen them mid-task.

1. **libdwarf from Homebrew**, the same way Capstone arrives. Its licence is the reason this was a research question, and the question is answered below rather than assumed.
2. **The milestone delivers the symbol view *and* the source view.** That is the proof the spec's milestone table names, and the line table measured below is what makes the second one reachable.
3. **A dSYM is looked for next to the binary first, then through Spotlight by UUID, then supplied by hand.** The order is measured, not stylistic: Spotlight does not index every directory, so a Spotlight-first design cannot be tested in a temporary one.
4. **Symbol resolution lives in the engine, behind the C contract.** Widgets never learn a file format; a consumer that only links the engine gets symbols too.

## What was verified before this plan was written

Measured on this machine (Apple Silicon, macOS 26.x) on 2026-09-13 with throwaway probes. Do not re-derive.

- **libdwarf's library is LGPL-2.1-only, and that is compatible with GPLv3.** Its `COPYING` says "The source code in the libdwarf directory is LGPL version 2.1" and "The source code in the dwarfdump directory is generally GPL version 2"; the library headers say "under the terms of version 2.1 of the GNU Lesser General Public License" with no "or later". §3 of the LGPLv2.1 lets a copy be taken under "the GNU General Public License, version 2 or any later version", which is how a GPLv3 project may use it. **This is the answer to open research question 2, and it is why libdwarf is not the Keystone case**: Keystone is GPLv2-only, with no relicensing clause to reach v3 through. `dwarfdump` is GPL-2 and is not linked or shipped.
- **The Homebrew formula is `dwarfutils`, aliased `libdwarf`**, version 2.3.2. It installs `lib/libdwarf.a`, `lib/libdwarf.2.dylib`, `lib/pkgconfig/libdwarf.pc` and headers under `include/libdwarf-2`. `Requires.private: zlib`.
- **Its pkg-config is not the Capstone trap.** `Cflags: -I${pkgincludedir}` names `include/libdwarf-2`, under which `#include <libdwarf.h>` resolves. Follow the `.pc` here; do not "correct" it.
- **The bottle is single-architecture** (`lipo -archs libdwarf.2.dylib` answers `arm64`). That is a milestone 10 problem, identical to Capstone's, and is recorded in the spec by Task 9 rather than solved here.
- **libdwarf reads a macOS dSYM.** Against a fixture built with `cc -g -c` then linked and passed through `dsymutil`, `dwarf_init_path` on `…dSYM/Contents/Resources/DWARF/<name>` returned `DW_DLV_OK`, the CU header reported **DWARF version 5**, `DW_TAG_subprogram` DIEs gave `add_two` at `low_pc=0x100000460` and `main` at `0x100000480` — **the same addresses `nm` reports** — and `dwarf_srclines_from_linecontext` returned 10 rows, the first being `0x100000460 probe_target.c:2`.
- **`dsymutil` needs the object files.** Compiling and linking in one `cc -g` command produces a dSYM with no debug info and the warning `no debug symbols in executable (-arch arm64)`. Compile to `.o`, link, then `dsymutil`. The test fixtures must be built that way.
- **`LC_SYMTAB` is readable from the target's memory, for shared-cache dylibs too.** A probe walking its own `_dyld_image_*` list and reading `__LINKEDIT` found: the main executable 10 symbols (`_main`, `__mh_execute_header`), `/usr/lib/libSystem.B.dylib` 106, `/usr/lib/system/libdyld.dylib` 1925, `/usr/lib/libobjc.A.dylib` 1499, each with names and `n_value`s. The counts are small for the system dylibs because the shared cache keeps their local symbols elsewhere; exported symbols are there, which is what a debugger names call destinations from.
- **The address of the symbol table is computed, not stored.** `symoff` and `stroff` are file offsets; in memory they are reached as `__LINKEDIT.vmaddr + slide - __LINKEDIT.fileoff + symoff`. The `Segment` struct already carries `vmAddr` and `fileOffset`, so nothing new is needed there.
- **Spotlight finds a dSYM by UUID, in an indexed directory only.** `mdfind "com_apple_xcode_dsym_uuids == 92966E93-3CBD-3CEF-8D05-727E934F295D"` answered nothing for a dSYM under `/private/tmp` and answered the path immediately for the same dSYM copied to `~/Downloads`. **A test that relies on `mdfind` in a temporary directory tests nothing.**
- **`DbgModule` already carries what a lookup needs**: `base`, `slide`, `uuid[16]`, `hasUuid` and `path`.
- **`macho::Image` deliberately stops short of this.** Its header says `LC_SYMTAB`, `LC_FUNCTION_STARTS` and chained fixups are "later milestones — deliberately absent rather than parsed-and-unused". Task 2 is that later milestone for the first of the three.

**Left to measure, by the task that needs it:** whether a stripped release-built fixture still yields useful `nlist` entries (Task 3 Step 6), and what `dwarf_highpc_b` reports for a DWARF 5 `DW_AT_high_pc` — offset form or address form — on these fixtures (Task 5 Step 4).

## Task 3: `nlist` symbols from a module

**Files:**

**Interfaces:**

```cpp
namespace MachBug::symbols
{
    struct Symbol
    {
        std::string name;
        uint64_t address = 0;   // runtime: the slide is already applied
        bool isFunction = false;
    };

    // Reads the module's symbol table through `reader`. `slide` is DbgModule::slide, and
    // `imageAddress` is what the reader's addresses are relative to -- 0 for a file, the load
    // address for memory.
    bool ReadNlist(macho::Reader& reader, uint64_t imageAddress, const macho::Image& image,
                   uint64_t slide, std::vector<Symbol>* out, std::string* error);
}
```

- [ ] **Step 1: Open the issue**, naming the measurement this rests on: `__LINKEDIT.vmaddr + slide - __LINKEDIT.fileoff + symoff` is where the array is in memory, and shared-cache dylibs answer there too.

- [ ] **Step 2: Write the failing test** against the `known_function` fixture, which publishes its own function's address through `LaunchAndReadPublishedAddress` — the helper every breakpoint test already uses, so the expected address is the fixture's own claim rather than this test's guess:

```cpp
TEST_CASE("nlist names a function in a live target")
{
    RecordingDebugger debugger;
    const uint64_t published =
        MachBug::test::LaunchAndReadPublishedAddress(debugger, FIXTURE("known_function"));
    REQUIRE(published != 0);

    // Modules::Enumerate is empty at the first stop -- its header says so and the modules tests
    // resume once before asking. The fixture has already run to publish its address, so the list
    // is populated here, and the main executable is dyld's first entry.
    std::vector<MachBug::Modules::Image> images;
    std::string error;
    REQUIRE(MachBug::Modules::Enumerate(debugger.GetTaskPort(), &images, &error));
    REQUIRE_FALSE(images.empty());
    const MachBug::Modules::Image& main = images.front();

    MachBug::macho::MemoryReader reader(debugger.GetTaskPort());
    MachBug::macho::Image image;
    REQUIRE(MachBug::macho::Parse(reader, main.loadAddress, &image, &error));

    std::vector<MachBug::symbols::Symbol> symbols;
    REQUIRE(MachBug::symbols::ReadNlist(reader, main.loadAddress, image, main.slide, &symbols, &error));

    auto named = std::find_if(symbols.begin(), symbols.end(),
                              [](const MachBug::symbols::Symbol& s) { return s.name == "_known_function"; });
    REQUIRE(named != symbols.end());
    REQUIRE(named->address == published);
}
```

`Modules::Image` is `{loadAddress, slide, size, path}` — there is no `base` field, and the main
executable is `images.front()` because dyld publishes it first. Assert the path ends in
`known_function` rather than trusting the ordering silently.

- [ ] **Step 3: Run it and watch it fail** — no `ReadSymbols`, no `Nlist.cpp`.

- [ ] **Step 4: Implement.** Walk `nlist_64` entries, skip `n_un.n_strx == 0` and empty names, apply the slide to `n_value`, and set `isFunction` from `(n_type & N_TYPE) == N_SECT` with `N_STAB` bits clear. Bound every string read by `strSize`: a `n_strx` past the end is a corrupt table, not a crash.

- [ ] **Step 5: Run it and watch it pass.**

- [ ] **Step 6: Measure the stripped case.** Add a test that reads a system dylib from the target's memory — `libSystem.B.dylib`, which has no file on disk — and assert it yields symbols with names. **Record the count in the test's comment**; the probe measured 106, and a future change that drops it to zero should fail loudly rather than quietly.

- [ ] **Step 7: Commit and open the pull request.**

## Milestone 7 exit criteria

On a clean checkout:

```bash
export QT_ROOT_DIR="$(brew --prefix qt)"
./scripts/check-toolchain.sh && ./scripts/verify-vendor.sh && ./scripts/check-credits.sh
cd src/cross
cmake --preset macos-arm64 -DMACHBUG_BUILD_TESTS=ON
cmake --build build/macos-arm64 --target MachBug_tests machdbg_disasm_tests
./build/macos-arm64/tests/MachBug_tests
./build/macos-arm64/tests/disasm/machdbg_disasm_tests
cmake --build build/macos-arm64
cd "$(git rev-parse --show-toplevel)" && ./scripts/check-bundles.sh && ./scripts/smoke-launch.sh
QT_QPA_PLATFORM=offscreen ./src/cross/build/macos-arm64/regview.app/Contents/MacOS/regview \
    --selftest src/cross/build/macos-arm64/tests/targets/known_line
```

All tests pass, and specifically:

- A loaded module's `nlist` symbols are read from the target's memory, including a dylib that has no file on disk.
- A dSYM next to its binary is found without Spotlight, and the Spotlight query is exercised or skipped with a printed reason — never silently.
- A function's name and its source line come back from DWARF, at the address `nm` reports for it.
- `SymFromAddr` answers a name and a displacement, and refuses an address in no module with a diagnostic.
- The symbol view shows named rows for the module the program counter is in, and `--selftest` fails if they are empty.
- The source view shows the fixture's own source line, and says so plainly when the file is absent.
- The x86-64 half is proven on the Intel runner, as every milestone since 3 has been.

What milestone 7 deliberately does not deliver: symbol *demangling* beyond what `nlist` and DWARF already carry; types, locals or expression evaluation against debug info; `LC_FUNCTION_STARTS`; a symbol server; and editing or reloading source while stopped.
